metadata support exists** for every one of the 275 columns, without assigning any

aggregation for scientific claims; magnitude or salience thresholds; humid-heat
or fire-weather pilots; literature ingestion or retrieval; embeddings; candidate
bridge generation, scoring or validation; QA construction. No profile number was
converted into a natural-language climate claim.

## 8. Methods and rules that affect scientific meaning

**No filtering, aggregation, unit conversion, renaming, imputation or exclusion
was applied. Nothing was type-coerced.** Every value was read as text and stayed
text. All 275 columns and all 62,834 rows are accounted for; none was dropped.

Rules applied that a reader must know to interpret the artifacts:

1. **Trimming for classification only.** A value is *empty* when
   `value.strip() == ""`, and the regexes are matched against the trimmed form.
   Distinct counts, top values, lengths and the reported sentinel candidates all
   use the **raw, unstripped** value, so no original byte is hidden.
2. **Regex matching is a statement about characters, not types.** A column is
   called decimal or integer only when *every* non-empty value matches the regex
   documented in `src/climrr/profile.py`. This says nothing about quantity or
   unit. `nan` and `inf` are deliberately rejected: `Decimal` parses them, but
   admitting them would make a minimum or maximum meaningless.
3. **A column with no non-empty values is not called decimal.** Vacuous truth
   would be a claim about a column that has no values to characterise.
4. **Ranges are exact.** `decimal.Decimal`, never `float`.
5. **`candidate_sentinel_values` is a frequency flag with no semantics.** A value
   is listed when it is a numeric extreme *and* occurs on ≥ 0.5% of rows. It is
   not a claim that anything is missing, invalid or special. That the rule flags
   the identifier column `TRACTCE` demonstrates its limits.
6. **Column identity is the ordinal index, not the name.** No name was renamed or
   deduplicated; truncated-looking names are carried verbatim.
7. **A stem match can never be `verified_from_dictionary`.** The dictionary names
   its fields by suffix within a per-variable section and never states that a CSV
   name's stem denotes that section, so the correspondence is an inference about
   how the export was built — the data owner's call. Such columns carry an
   explicitly EXECUTOR-authored candidate section and a question.
8. **Two EXECUTOR-authored maps exist and are labelled as such** in
   `src/climrr/dictionary.py`: a stem-to-section candidate map and a
   narrative-passage map. They exist only to make questions specific. Neither
   can promote a column to `verified_from_dictionary`.

## 11. Failures, rejected cases, and known limitations

**Fixed during the work package.**

- The four new scripts formatted paths with `Path.relative_to(REPO_ROOT)`, which
  raises for any path outside the repository. Every scratch-directed run crashed
  *after* writing its output. Found by running the runbook's own commands rather
  than by reading them. They now use `climrr.paths.repo_relative`.
- The profile CSV was written with `csv.writer`'s default CRLF, which Git would
  renormalise, making a committed artifact differ from the one the next host
  regenerates. Now written with LF.
- The secrets scanner flagged eleven lines in `src/climrr/profile.py` because the
  word chosen for a trimmed string is also a credential word. Following the D-006
  precedent, the prose and the variable were reworded rather than the guard
  loosened.

**Limitations that remain.**

- **The 21 verified columns are 7.6% of the table.** This is a property of the
  dictionary, not of the method: it names most fields by suffix within a section,
  and the CSV writes stem plus suffix. One answer (Q1) would move 75 columns.
- **83 columns have no dictionary support at all**, including all 56
  `precipdaily_*` columns and the seven socioeconomic columns. No amount of
  re-reading the document will resolve them.
- **`verified_from_dictionary` is a statement about the dictionary, not about the
  data.** It means the document states name, meaning and unit/scenario. It does
  not certify the values are correct.
- **The stem-to-section and narrative maps are EXECUTOR judgement.** They are
  labelled as such in code and in every question they generate, and they cannot
  promote a column to verified — but a reader who skims could still mistake a
  candidate for a fact.
- **The profile holds every distinct value in memory**, peaking near 1.5 GB. Fine
  on both hosts today; it would not scale to a much wider table.
- **Cross-host reproduction is unproven** until Sophia runs. The content hash is
  designed to make that comparison decisive, but it has not yet been made.
- The extraction leaves one of the 19 PDF pages with no text — page 3, confirmed
  empty by re-extracting page by page. Nothing in the field tables appears to be
  lost (11 sections parsed, matching the dictionary's own contents list), but
  this was not proven exhaustively against the PDF's visual layout.

## 12. Deviations from the approved plan

1. **Added `n_with_leading_zero_any`.** The work package gates
   `n_with_leading_zero` on `all_nonempty_match_integer`. Kept exactly as
   specified, and added an ungated count beside it, so a leading zero in a
   non-integer column cannot become invisible. Acceptance criterion 4 is about
   identifiers surviving, not about integer columns.
2. **Grouped the host-varying top-level fields under `environment`.** The work
   package lists `git_commit`, `hostname`, `location`, `pinned_libraries` and
   `python_version` as top-level. All are present, nested one level, so that "the
   JSON with the environment block removed" has a single unambiguous meaning. The
   remaining named keys (`data_sha256`, `data_bytes`, `n_rows`, `n_columns`,
   `decimal_regex`) are at the top level as specified.
3. **Added fields not requested:** `n_nonempty`, `n_distinct_nonempty`,
   `row_shape`, and the rule constants (`integer_regex`, `leading_zero_regex`,
   `sentinel_min_rate`, `encoding`). `n_distinct_nonempty` is what `is_constant`
   and `looks_unique` are computed from, per the work package's own
   parentheticals; recording it makes those two auditable.
4. **The cross-check compares six fields, not four.** Added `name` (so a
   positional mismatch cannot hide) and `n_with_leading_zero_any` (criterion 4
   under a second reader).
5. **Added `src/climrr/manifest.py`**, not named in the work package. Three new
   scripts each needed the fail-closed check; one implementation is better than
   three.
6. **Used `manual_candidate` for near-miss stem columns.** The work package
   defines the rule but not where to apply it. Columns like
   `tempmax_seas_rcp85_mid_summer`, whose name matches no field, would otherwise
   have been reported as "appears nowhere in the dictionary", which is misleading
   when `RCP85_MIDC_SUMMER` sits three characters away. They cite the near-miss
   and are `unresolved`.
7. **Introduced two EXECUTOR-authored maps** (stem-to-section, narrative). Not
   requested. Without them the questions would read "which of eight sections
   applies?" instead of naming one candidate and one line. They never produce a
   verified status. **If GUIDANCE considers this too much EXECUTOR judgement, the
   maps can be deleted and the affected columns fall back to `unresolved` with a
   less specific question; no other result changes.**
8. **Chose `pypdf` over `pdfplumber`** — the work package allowed either.
9. **Field 14 uses the nine M1-WP1 acceptance criteria** from the GUIDANCE gate
   review, as the work package directs, rather than the M1 milestone gate
   criteria in `PROJECT_PLAN.md`. M1 is not complete and its gate is not proposed.
10. **Added a usability gate to the extraction** (fails if pages, text volume or
    non-empty pages fall below a threshold), so the "PDF extraction is unusable"
    escalation is mechanical rather than a matter of opinion. It passed.

Nothing in the work package was skipped.
